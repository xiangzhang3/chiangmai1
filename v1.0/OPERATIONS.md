# Hourly paper worker contract

## Minimal-permission deployment

Prefer an authorized existing hourly task using the connected GitHub capability.
Do not create another writer until existing automations are inventoried. This
patch does not enable a GitHub Actions workflow or expand token permissions.
If a persistent runner with functioning public-data egress cannot be provided,
report the verified connectivity blocker and abstain. A schedule alone does not
establish continuous execution.

## Single source, single commit

1. Fetch the explicitly selected deployment ref, its runner code and
   `v1.0/runtime/state.json` using the connector. The published recovery ref is
   `paper-recovery-2026-10-10`; these files are not on main until a separately
   authorized merge. Do not silently substitute main. Retain the state blob SHA
   and base commit. Never start from a bundled old checkpoint or regenerate
   accounts after recovery.
2. Acquire the scheduler's single-writer lease. The local runner uses an advisory
   file lock and content compare-and-swap; that lock cannot serialize different
   machines. Only one automation may perform account mutations. Other jobs may
   read data and produce research reports without writing account state.
3. Run tests and execute one fresh-data scan. The canonical idempotency key is
   `hourly:<UTC Unix hour>`, generated by the runner. Re-running an already
   recorded key produces ALREADY_RECORDED without another entry, close or fee.
   An interrupted scan has no recorded fills until its state commit succeeds.
4. Publish the whole updated `runtime/state.json` in one GitHub file update with
   the exact original blob SHA. Never force a ref or overwrite a newer state.
   Account changes, evidence, run IDs and audit events are contained in this one
   document and commit together. A stale-SHA rejection means discard the staged
   update, reload latest state and reconcile. Never replay a fill onto a newer
   ledger or re-use the old quote after expiry.
5. Re-read the remote file and verify expected revision, run ID, event digest and
   account balances before reporting a paper order as durably recorded. A local
   output with PAPER_OPEN/PAPER_CLOSE is only staged until this succeeds.
   Uncertain publication must be read back, not blindly retried.
6. If publication failed, report the ledger write blocker. Do not claim an order
   was recorded. Future workers must resume from the remote authoritative file,
   not a failed local simulation result. Keep known account state unchanged.

## Recovery and data integrity

- Preserve `qingmai/sim_accounts/KAIA-A01.json` as the historical checkpoint.
- Do not concurrently let an older task continue updating that legacy file.
  Resolve writer ownership explicitly before deployment; do not assume it stopped.
- JCT remains ACCOUNT_STATE_UNVERIFIED until prior balances/positions/fills are
  reconciled or the user expressly approves a separately named prospective test.
- No historic fills, fees, funding or net returns may be invented. Never use
  an unknown JCT balance as a flat 1,000 USDT reset.
- Verify wall clock against Binance server time. More than 30s discrepancy blocks
  execution. Quote, book and mark must be <=60s old; future timestamps >5s fail.
- Public read failures are recorded as ABSTAIN, with stale equity labelled.
  Account-state-unknown and market-data-unavailable are separate blockers.
- Raw successful snapshots are content-addressed in `market_evidence`; each
  event includes a SHA-256. Keep history. When file size makes one-file commits
  impractical, migrate with an explicit versioned, atomic storage plan; do not
  silently truncate evidence or trades.

## Evaluation discipline

The recovered strategy version is a prospective experiment. Compare variants
in separate, explicitly budgeted accounts; do not pool their P&L or optimize on
the evaluation window. Track duration, sample count, net costs and missed-data
periods. Freqtrade/VectorBT integration and walk-forward research are separate
uncompleted work. No profitability conclusion follows from unit tests.

## Observation-only hourly collector

A separate public-market observation task may run while account-writer ownership
is unresolved. It must never mutate `runtime/state.json`, the legacy checkpoint,
or main. Only the explicitly selected recovery branch is authorized here.

- Store one immutable file per symbol per UTC hour at
  `v1.0/runtime/ui_observations/YYYY-MM-DD/HH-SYMBOL.json`.
- Read the hour path first; if it already exists, validate it and skip. Never
  replace an earlier observation with a later quote for the same hour.
- Record actual `observed_at` capture time with timezone, the exact approved
  official symbol-page `source_url`, `symbol`, and supported numeric `fields`.
  The schema and research-only inspector are in `runtime/ui_observations/README.md`
  and `qingmai/ui_research.py`. No account or private financial information.
- Missing or unverified fields remain absent; do not fill from an aggregate
  price service or infer venue-event timezone from capture time.
- To publish several missing files atomically, create a tree/commit from a freshly
  read branch head, then update that branch with `expected_sha` and `force=false`.
  A stale-head rejection requires rereading existing paths and reconciling; no
  blind retry. Read back files at the resulting commit before claiming storage.
- An observation is research only and cannot produce or alter a paper fill.
  Capture-time records do not establish continuous execution or full signal
  eligibility. Do not report monitoring as a restored trading deployment.
